# Catalog and accommodation imports

## Product catalog import

`/admin/commerce/catalog-imports` is an admin-only, bounded Digikala import framework. It is gated by the existing feature-flag control plane under `catalog.import.digikala`; a missing flag is OFF, and a second administrator must approve any change. It must remain off until authorized source access and the applicable text/image reuse permissions have been verified. When authorized, the admin supplies a source product/category URL and maps the destination to an existing PET LIFE category; optional brand mapping is an explicit admin choice. Requests are idempotent and persisted as jobs with progress, cancellation, retry/backoff, per-item results and restart recovery. A job is limited to 20 URLs, 10 pages and 100 products (the admin screen currently uses 5 pages/50 products).

The parser consumes only public Schema.org `Product` JSON-LD from HTML. It does not call Digikala's unofficial seller or internal APIs. It records product name, any explicitly supplied alternate name, brand/category text, description, structured specifications, canonical URL and gallery candidates. No machine translation is fabricated. The feature is currently off: no source metadata or image is fetched or copied while its flag is off. Since the catalog decision C-03 requires exactly three images, after permissions are verified and the flag is approved, import requires three validated images; insufficient media remains in `NEEDS_REVIEW` and does not create a catalog product.

If enabled after the above authorization check, imported items create a `Product` with `DRAFT` status, exactly three repository-owned `ProductMedia` rows and no `ProductVariant`, seller offer, price, inventory, order, or transaction. Source image bytes are type/signature/size checked, fetched only from allow-listed Digikala hosts over the existing SSRF-safe fetcher, and copied to the existing storage driver; this path must not be enabled without documented reuse permission. The source media URLs remain on the media/source observation for provenance; the image is not transformed, so any source watermark is preserved. Repeated source observations do not mutate the product. A changed source snapshot stays pending until an admin explicitly applies or rejects it with a reason and an audit record.

The source's live terms and detailed product-page layout were not established by this implementation pass. A small read-only pilot on 2026-11-06 fetched `robots.txt` (HTTP 200) and a product-category URL present in Digikala's published sitemap (HTTP 200, 13,628 bytes). That page returned a Next.js `/routing` shell rather than category results or Product JSON-LD. Pilot: 1 category URL tested, 0 products discovered, 0 imported, 0 skipped, 1 failed schema/content check. No source price or stock was read or imported. Thus, the importer code remains tested only with synthetic parser fixtures; do not claim live product import compatibility. The public page access alone does not establish content or image reuse permission. The importer fails closed for query URLs, honors robots rules, and does not retry access denials, 429s, disallowed paths, or private/unsafe URLs.

### Daily pet-permitted stays — 2026-11-11 (supersedes the first-page pilot above)

Owner instruction (2026-11-11, PL-03/PL-10): show Jajiga's pet-accepting stays to members, refreshed daily, with each card sending the member to the exact Jajiga listing.

- **Why nothing was visible before.** Production `JAJIGA` was already `AUTOMATED/SUPPORTED`, but every scheduled run since 2026-11-09 failed `MALFORMED: Jajiga search result had no numeric listing id`: the first-page HTML server-renders one card plus five empty placeholders, and one placeholder aborted the run. Even a successful run would have published nothing, because every record stayed `partial` (status `DISCOVERED`) and `autoPublish` was off.
- **Source used.** `GET https://api.jajiga.com/api/search?perPage=18&rules[]=pet&page=N` — the JSON endpoint the jajiga.com search page calls in an ordinary browser session, with no login, cookie, token or proof-of-work. `api.jajiga.com/robots.txt` is `User-agent: * / Allow: /`, re-checked at the start of every run. Recorded as `UNOFFICIAL_PUBLIC_WEB_ENDPOINT`, not a partner API.
- **Observed 2026-11-11.** `filters.rules = ["pet"]`, `rooms.pagination.total` 2,831–2,832, 18 per page, page 158 short (6), page 159 empty; every card carried `is_pet_friendly`. A read-only dry run of the new adapter over robots + 3 pages produced 54 listings in 39 cities, all with title, city, province, capacity and a from-price.
- **Run shape.** One request at a time, 2.5–4 s apart, honest User-Agent, ≤ 300 requests per run (~160 today, roughly 9 minutes once a day). The response must echo the pet filter or the run fails closed; a card without a numeric id, without the pet marker, or repeated across pages is skipped. A 403/CAPTCHA/429 stops the run and opens the circuit with no retry or bypass; any other failure after some pages keeps what was seen and marks the crawl incomplete, so nothing is aged out. Only a complete walk counts misses (STALE after 2, removed after 4).
- **Stored per listing.** Jajiga id, canonical `https://www.jajiga.com/room/{id}`, title, city, province, max guests, bedrooms, rating + review count, instant-booking marker, the source pet-filter evidence, and a nightly `FROM_PRICE` (toman × 10 = IRR) with its observation time. **Not stored:** descriptions, pictures, host identity, coordinates, invoices. No date-specific availability or quote is claimed; members confirm dates and pet rules on Jajiga.
- **Publication.** Explicitly marked cards are published automatically (`autoPublish = true`); staff can hide any listing or pause the source from the travel ERP. The outbound link logs a click and 302s only to the validated Jajiga room URL.
- **Terms.** Article 10 of jajiga.com/rules (observed 2026-11-10) restricts extraction/reuse of platform data without written permission, and **no written permission is on file**. The integration runs on the owner's choice of a daily click-out (see "Licence status" above) with factual metadata and outbound links only; pause the source if Jajiga objects, and prefer a written agreement or official feed when one becomes available.
- **First run and resilience fixes (2026-11-12).** The first scheduled run (2026-11-11 22:13–23:30 UTC) published 2,340 stays but stopped after 131 of 158 pages while the VPS was under build load (each page took ~34 s instead of ~0.2 s), and it was recorded as `SUCCEEDED` with no error. Now: a page that times out or gets a 5xx is asked for again after 15 s and then 45 s (403/429 are still never retried); a crawl that still ends early — or runs out of its request budget or page cap — is recorded as `PARTIAL` with a `DISCOVERY_INCOMPLETE` error naming the page and cause, and the source shows `DEGRADED` with that reason; nobody is aged out. `timeoutMs` is 20 s and the budget 300 requests. The DNS lookup now sits under the same timeout. The source lock is refreshed while a run is alive, and a run holding its lock is never marked `ABANDONED`. The daily interval is counted from the last run's start (a 77-minute crawl no longer pushes every later run back by 77 minutes), and a run that failed on a timeout/5xx is retried an hour later, at most three times, instead of the next day.
- **Member search fixes in the same change.** The `guests` condition no longer overwrites the pet-policy condition (the web always sends `guests`, so the default exclusion of explicit "no pets" listings and the `petPolicy` filter were silently dropped). Without a price filter, search paginates in the database with an exact total instead of loading and pricing up to 500 rows per request; results are ordered by rating, review count, then id. A city query also matches the province.

## Operational boundary

- The importer is admin-only (`commerce.view` to read, `commerce.manage` to queue/cancel/review).
- The Digikala importer is unavailable by default. Do not create/enable `catalog.import.digikala` until written access and reuse permission are verified; flag changes use the existing second-admin approval and audit mechanism.
- Rejected or blocked source access is surfaced as job/item error or an operator task after terminal job failure; no proxy, identity rotation, undocumented endpoint, or synthetic source result is used.
- Empty product categories and import queues remain genuinely empty. A no-result job is a failure/partial result, not a simulated success.
- Accommodation links remain original-source outbound links. No booking, payment, live availability or guaranteed pet acceptance is represented by these imports.

### How Jajiga stays are shown — 2026-11-13 (owner: honest display)

Jajiga marks a stay as pet-friendly and publishes nothing else about pets. The cards and the detail page say exactly that:
- Pet line: «طبق اطلاعات جاجیگا، این اقامتگاه پت‌پذیر است؛ شرایط حیوان و ظرفیت تاریخ سفر را با جاجیگا یا میزبان بررسی کنید» (the same sentence in en/de/es/ar/nl). "Verified"/«تأییدشده» appears only when opetlife staff confirmed the policy (`pet.authority = ADMIN_CONFIRMED`). The API's trust label for a source's own marker is `PET_POLICY_SOURCE_REPORTED`, and `PET_POLICY_CONFIRMED` is reserved for staff confirmation.
- Pet conditions — species, size, indoor access, pet fee, host approval — each read «نامشخص» (unknown) unless the source states them. For Jajiga all five are unknown.
- Price: «شروع قیمت» (Jajiga's nightly from-price) with "updated … ago" from the stay's last successful sync. It is never presented as the price for the member's dates.
- The button names the source ("View this stay on Jajiga") and goes through the logged `/travel/external/stays/{id}/out` redirect to the exact `https://www.jajiga.com/room/{id}`.
