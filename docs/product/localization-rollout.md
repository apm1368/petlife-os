# Localization rollout status

The public landing route is available in Persian, English, German and Spanish. Persian uses RTL; the other three use LTR. The German and Spanish landing copy includes the public navigation, service descriptions, partner entry, trust/privacy copy, footer and image-credit disclosures. The existing approved landing composition and source images are unchanged; the German and Spanish hero use the existing English-labelled artwork because the pavilion labels are baked into the image.

This is not full application localization. The account preference API and database support saving all four locales (fa/en/de/es). The shared member navigation (desktop, mobile and Explore sheet), Explore index and Account navigation now have explicit copy in all four locales; links retain the active locale. Registration, password login, phone/OTP login, forgot/reset password, auth-shell copy and household collaboration copy also have German/Spanish translations. Household copy covers members, invitations, pet permissions, access presets, confirmation actions and access history. Account dates use the selected locale (fa retains Jalali) and account counts use locale-specific number formatting. The DE/ES auth catalogs overlay the English catalog so unfinished message keys remain readable instead of raising missing-key errors. These page families have focused component tests. The landing and personal-settings locale selector/calendar explanation were already localized in all four languages.

Account settings page bodies (outside the language/calendar copy), pet/health, booking, provider, seller, orders/repeat delivery/favorites, admin, support and legal copy remain partially or mostly Persian/English only. German and Spanish catalogs translate auth, household, landing, personal settings, pet profile/care, shop discovery/cart and checkout branches documented below; other keys fall back to English to avoid missing-key errors. Notification and trip-checklist copy also falls back to English for German and Spanish; German/Spanish SMS templates are not implemented and must not be simulated. Outside the components named above, do not present fallback text as a completed translation.

### Shop discovery and cart (PR slice based on #118)

German and Spanish now have explicit copy for customer shop home, catalog search/results and filters, product details, compatibility guidance, cart, stock/rating labels, and shared commerce navigation/feedback. Shop-facing prices retain the same Rial-to-Toman display conversion; only digit grouping follows fa/en/de/es locale. Persian stays RTL with Jalali behavior unchanged; English remains the fallback source. Product titles, seller names, brands, catalog data and offer values remain server-provided data, not translated or fabricated.

Not included: order history/details, repeat-delivery management, favorites, seller onboarding/catalog/offer management, and commerce backoffice. These remain English fallback in German/Spanish. Checkout (address, delivery, safety acknowledgement, review, shipping, payment, financing, pending and failure states) now has German and Spanish copy in PR #132, based on shop/customer localization PR #122. Locale-aware Rial-to-Toman grouping is retained, Persian Jalali/digit behavior is unchanged, and checkout address summaries use locale-aware list separators. Focused checkout and currency tests pass locally; hosted CI is pending. German/Spanish SMS templates and delivery are still absent.

### Travel discovery results (PR #131)

German and Spanish translations cover travel search result filters, accommodation type and pet-policy labels, result metadata, dates, and localized numeric/currency formatting. The PR's current head `4515b779` is based on #118 and its required CI build passed; it is still awaiting review. The import/source boundary is unchanged: results reflect stored discovery snapshots and do not promise live availability or a reservation. Details and other travel-management screens may still use English fallback.

Next slices: orders/repeat-delivery/favorites and seller catalog; provider/booking; support/legal; travel/community/partner; backoffice and notifications. Each slice must include locale-aware date/number formats where relevant, route-preserving language switching, accessibility, tests and a missing-key check before it is reported complete. Account language persistence remains covered by the existing #118 API/database implementation; this batch does not alter that contract. PR #132 depends on #122 for shared commerce messages and locale-aware currency behavior; it must be retargeted after #122 merges and its affected checks rerun.
