# بازگشت امن به ثبت هویت پت

مبنای پیش از تغییر: `98b61188fa86b77cbfbcc300356a3a0280f7cc3d`؛ همان درخت کد انتشار #33. بازگشت سرد به مرحلهٔ سن، وقتی نام و گونه هنوز فقط در حافظه بودند، دکمهٔ رد کردن را بی‌اثر می‌کرد. دو تصویر واقعی پیش از تغییر در اندازه‌های ۳۹۰ و ۱۴۴۰ این حالت را با صفر درخواست نوشتن ثبت می‌کنند.

## تغییر

- حداقل اطلاعات ذخیره‌نشده دوباره درخواست می‌شود؛ پیش‌نویس همان خانواده حفظ و پیش‌نویس خانوادهٔ دیگر پاک می‌شود. تاریخ تولد اختیاری می‌ماند.
- شناسهٔ پت در همان تراکنش ساخت، فقط به جریان هویت درخواست‌کننده در همان خانواده وصل می‌شود. قطع درخواست بعدی ذخیرهٔ مرحله، شناسه را از بین نمی‌برد؛ ورود مجدد پت موجود را می‌خواند.
- نام فارسی برای هدر Idempotency-Key رمزگذاری می‌شود؛ مقدار نام در بدنه فارسی می‌ماند. پیش از اصلاح، مرورگر هدر غیرمجاز را قبل از ارسال رد می‌کرد.
- قرارداد API، Prisma schema و migration تغییر نکرده‌اند. این تغییر ادعای تضمین یکتایی همهٔ درخواست‌های همزمان یا همهٔ جریان‌های ساخت پت ندارد.

### ثبت پت با API و PostgreSQL واقعیِ ایزوله

دوازده جریان (سه خطا × fa/en × 390/1440) با AppModule واقعی، PostgreSQL/PostGIS و Redis تست اجرا شدند؛ sessionهای fixture فقط برای کاربران مصنوعی همان DB با ابزار رسمی امضای نشست ساخته شدند. احراز هویت، CSRF و مجوزهای محصول فعال بودند؛ CORS فقط در harness و پیش از init برای دو پورت loopback فعال شد. این آزمون ورود با رمز یا OTP واقعیِ سایت نیست.

- بازگشت سرد از checkpoint سن با نام/گونهٔ حافظه‌ایِ ازدست‌رفته به اطلاعات اولیه برگشت. نام فارسی در بدنه حفظ و هدر Idempotency-Key واقعاً ASCII بود.
- در چهار جریان، POST واقعی commit شد و پاسخ آن در مرورگر قطع شد؛ پس از reload کامل که Zustand را خالی می‌کند، GET واقعی progress و pet همان پت را بازیابی کردند. ردکردن سن نامعلوم به عکس رسید؛ فقط یک POST ساخت و یک پت در DB وجود داشت.
- در چهار جریان دیگر، انتخاب ۱۴۰۳/۱/۱ با جابه‌جایی تقویم به ISO `2024-03-20` رسید و POST واقعی ذخیره شد. پاسخ ۵۰۳ ذخیرهٔ مرحله پیش از نوشتن progress تزریق شد؛ پیام خطای مشخص و سال انتخابی حفظ شدند. پس از reload، همان پت بازیابی شد؛ تغییر به سن فارسی «۰» با PATCH واقعی، birthDate را null و approximateAgeMonths را 0 کرد. پت دوم ساخته نشد.
- چهار جریان اضافه، قطع پاسخ موفق و سپس تغییر تاریخ به سن صفر بدون reload را بررسی کردند: پیش از اصلاح، پاسخ cache تاریخ قبلی را نگه می‌داشت؛ اکنون همان petId با PATCH اصلاح می‌شود. هیچ pageerror یا overflow پس از بازیابی در دوازده جریان نبود. [خروجی و ۲۴ تصویر خطا/بازیابی](./onboarding-qa-screenshots/isolated/checks.json). این موارد، یکتایی درخواست‌های موازی یا همهٔ قطع‌های شبکه را ثابت نمی‌کنند.

### جداسازی پیش‌نویس خانواده

چهار جریان fa/en × 390/1440 جداگانه در [خروجی خانواده](./onboarding-qa-screenshots/family/checks.json) ثبت می‌شوند: رفت‌وبرگشت واقعی NextLink با marker ثابتِ document، پیش‌نویس همان خانواده را در حافظه حفظ می‌کند؛ تغییر خانواده از API واقعی، گونه/نام خانوادهٔ قبل را پاک می‌کند. ساخت بعدی فقط در خانوادهٔ جدید انجام می‌شود؛ خانوادهٔ قبلی صفر پت دارد. این موارد جای آزمون API مجوزها را نمی‌گیرند.

اجرای مجدد ابزار ابتدا به‌دلیل selector برچسب انگلیسی و یک بار نبود harness آماده متوقف شد؛ نتیجهٔ ناقص موفق شمرده نشد. selector به نقش textbox محدود به همان صفحه اصلاح شد؛ assertion خالی‌بودن نام، تعداد پت DB، حفظ document و نبود overflow/pageerror حفظ شدند. CORS و مسیر اجرای harness نیز فقط در ابزار تست اصلاح شدند؛ تنظیم اتصال محصول/Claude تغییر نکرد.

### همزمانی محدود و محدودیت یکتایی پایدار

در baseline محلی شش درخواست همزمان با یک کلید شش پت ساختند. CI اولیهٔ PR روی b04a7ec نیز شکست خورد: ۷۷۱/۷۷۲ موفق، آزمون جدید همزمانی با خطای transaction/pool. [اجرای ناموفق](https://github.com/apm1368/petlife-os/actions/runs/39002153589). آزمون ضعیف نشد؛ اکنون صریحاً یک پت و یک شناسه می‌خواهد.

اصلاح فقط برای endpoint پت، lease اتمیک Redis با مهلت ۳۰ ثانیه و انتظار حداکثر ۱۰ ثانیه دارد؛ نتیجه پیش از پاسخ cache می‌شود. پاسخ نامطمئن 409/503 است و خودکار عملیات را تکرار نمی‌کند. در بررسی واقعی با pool پنج‌اتصالی، شش درخواست همزمان → یک پت/یک شناسه؛ ۴۸ تست در چهار suite گذشتند. namespace عملیات مالی تغییر نکرده است.

این راهکار تضمین پایدار exactly-once در پایان lease، مرگ process، حذف/شکست Redis، پایان TTL بیست‌وچهارساعته یا کلیدهای متفاوت نیست. بدون کلید، دو درخواست دو پت مستقل می‌سازند. این محدودیت باز است؛ schema/migration جدید اضافه نشد.

### نتیجهٔ آزمون‌ها و بازتولید

۲۲ آزمون وب در چهار فایل گذشتند؛ شامل سه regression برای پاسخ cache قدیمی، تبدیل تاریخ/سن صفر و نگهداری شناسه/پیش‌نویس پس از شکست PATCH. اجرای نهایی API روی DB تازه پس از اعمال واقعی ۸۸ migration موجود: ۲۶۲/۲۶۲ آزمون در پنج suite موفق، بدون skip یا تغییر timeout؛ شامل app، pet-identity، onboarding-qa، subscription و notifications-activity-subscription. آزمون همزمانی نهایی نیز شش درخواست → یک پت/یک شناسه بود. CI نهایی مستقل در checks همین PR و Issue #4 ثبت می‌شود.

دو اجرای گستردهٔ محلیِ پیش از محیط تازه، timeout/ECONNRESET در auth و سپس timeout در پرداخت شبیه‌سازی‌شده داشتند؛ هیچ assertion، timeout یا workflow تغییر نکرد. علت قطعی این ناپایداری‌های محیط قبلی تعیین نشده و نتیجهٔ دیتابیس تازه/CI، شاهد جداگانه است. آزمون اولیه روی کد main سه شکست از ۱۲ مورد داشت (۹ موفق)؛ سه شکست همان یافته‌های بالا هستند، نه خطای محیط.
